# ADR-0002：Jev state 用英文坐标记法，三问并行一次发出

- 状态：accepted（2026-09-28）
- 背景：Jev 只收文本/结构化 state，官方口径中文精度较低；棋盘局面天然适合坐标记法。

## 决定

1. 每个引擎的 `serializeForJev` 产出**英文** `state`：盘面说明（尺寸/坐标方向）+
   双方棋子坐标数组 + 上一手 + `legal_moves` 列表。
2. 走棋固定为一次请求三问并行：`move`（Choice，每个合法着法一个选项）+
   `edge`（Noul，是否占优）+ `position`（Score，0–10 局势分）。
3. Choice 选项 ≤255，超出预筛（邻近棋子+关键点+随机补齐）。

## 后果

- 优点：一次前向拿全三类信息（官方口径：加问题几乎不增延迟，只多花输入 token）；
  概率分布直接被 `BG.jev.decide()` 消费，无文本解析，无幻觉空间；
  坐标记法紧凑，单步 state 0.5–1.5K token ≈ $0.00005。
- 缺点：prompt 与 criteria 需英文维护；概率判断本身可能错（以棋盘胜负为准）。
- 约束：禁止把一次决策拆成串联多请求（既违背设计原则又放大成本/延迟）。

## 考虑过但放弃

- 中文记法（如"炮二平五"）：官方口径中文精度较低，且各棋种记法不统一。
- FEN/PGN 等标准记法：部分棋种（中国跳棋）无标准记法，统一用坐标最简。
- 单问（只问 move）：会丢失局势判断信息，决策面板的 edge/score 展示即依赖并行问。
