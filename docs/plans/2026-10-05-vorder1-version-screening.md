# vorder1：版本排序筛查（v11 / v13 / v14 三对，2026-10-04 夜 → 10-05 凌晨）

> **这份结果只回答一个问题：下一步跑什么**（补一对决赛，还是跑完整 L1）。它**不是版本排序结论** ——
> 每对 20 局、Wilson 半宽 ±20 pt，按 [阶梯计划](2026-10-03-tactics-fidelity-and-elo-ladder.md) §7 的纪律，
> 这个量级只配当筛查，不配下「谁更强」的结论。

## 1 为什么跑

[L2](2026-10-04-l2-version-vs-rapfi.md) 把 5 个版本各 60 局地摆到 Rapfi 三档面前（300 局），结果是：
**每个版本都明显强于 Rapfi，但版本彼此分不出来**（12 对 Wilson 区间互相重叠，名义第一 v11 85.8%、
名义最末 v13 71.7%）。按阶梯计划 §7 的「Stage 1 筛选 / Stage 2 决赛」纪律，先在**版本互打**上花 60 局筛一遍，
比直接上 L1（10 对 × 20 = 200 局、≈11 h）划算：筛出差距就只补那一对决赛，筛不出就老实跑 L1。

业主 2026-10-04 批准了这条三对筛查（同一轮还定了把 Rapfi 曲线直接补到 UI 上限，即 L4）。

## 2 方法

```bash
node scripts/experiment-ladder.mjs \
  --identities 'official:v13-pressure-gate:0,official:v11-vct:0,official:v14-live3-fresh:0' \
  --games 20 --batch vorder1 --poll 60
```

| 项 | 值 |
| --- | --- |
| 配对 | 3 对（`crossPairs` 顺序）：r1 `v13 vs v11`、r2 `v13 vs v14`、r3 `v11 vs v14` |
| 每对局数 | 20（同一对内部换色双跑，先后手配平） |
| 总规模 | 60 局 |
| 运行面 | `--store local`（不写业主 D1）＋`--upstream direct`（不经过业主 Worker） |

| 开局库 | **未启用** ⇒ 只排掉了先后手，没控制具体开局形态（与 L2 同口径，便于并读） |
| 计时口径 | Rapfi 侧按**墙钟**（`INFO timeout_turn`），上游侧按 **token**；每手 `tac_ms` 与模型往返分开记（m07650） |
| 串行纪律 | 一次只跑一条 —— Rapfi 的思考时间是墙钟，两个作业同时跑会抢 CPU 让档位失真（`--parallel` 被拒跑） |
| 零 CF 触碰 | 按设计零写入：`--store local` 只落 box 上的 JSONL，上游走直连（`--upstream direct`）不经业主 Worker；日志逐轮打 `store=local：未触碰业主 Worker`。本机已无法读 D1（`7403 not authorized`，见 `docs/status.md` 已知限制第 29 条），故不再重复「跑前跑后计数」的核对 |

三轮各自的 tag 为 `exp-20261004133730-vorder1-r{1,2,3}`，产物留在 box 的

## 3 结果

### 3.1 三对逐对（判强弱只看这张表）

| 对（A vs B，A 取字典序在前） | 局数 | A 胜/和/负 | A 得分率 | Wilson 95% |

| `official\|v11-vct\|0` vs `official\|v14-live3-fresh\|0` | 20 | 3/11/6 | **42.5%** | [23.8%–63.6%] |

三对的方向是 **v11 > v13 > v14 > v11**：一个**闭环**，而且三对的得分率全都是 **57.5% / 42.5%**。

- 三个身份各 40 局（20 黑 + 20 白），**得分率全是 50.0%**、BT Elo 1487.4 / 1500 / 1512.6（BT Δ 区间都是 ±50 上下）。
- 也就是说：**在 60 局的样本上，这三个版本没有任何一个比另外两个强得能被看见** ——
  这比 L2 的「12 对区间重叠」更进一步：连方向都自相矛盾。

## 6 不能说什么（读数的硬边界）

1. **不能给版本排序**：每对 20 局、Wilson 半宽 ±20 pt；区间重叠就不许说「A 比 B 强」。
2. **不能把 20 局的胜负读成机制好坏**：接管层的「层 × 结果」是**相关性**，不是因果 ——
   某层开火多、且多落在和棋/败局，可能只是「局面本来就到了那一步」。
3. **不能当成 L2 的重复**：L2 的对手是 Rapfi（固定引擎、固定预算），本轮对手是自己人（同一个上游模型）——
   同门对局更容易互守成和，别把两批的和棋率直接比。
4. **开局形态不受控**（与 L2 相同）：只排掉了先后手。

## 7 对下一步的硬性影响

1. **筛查规则判定 = 跑 L1；但先把算术摆出来**：L1 是 10 对 × 20 局 = 200 局，按本轮实测 4.6 分钟/局
   ≈ **15.5 小时**。而它每一对仍然只有 20 局 —— 本轮已经证明「三对 20 局的闭环」能出现，
   所以 L1 的 10 对 20 局同样**排不出稳定名次**（P5 的结论：200 局才勉强分辨 ~30 Elo；
   而这三版的真实差距看起来 ≤5 pt）。⇒ **L1 只值当「看梯队有没有分层」**，
   若要真排这 3 版的先后，需要按对堆到 100–200 局（3 × 100 = 300 局 ≈ 23 小时），
   这已经大于「把 Rapfi 曲线补到 UI 上限」（L4，≈13–17 小时）。
2. **L4 正在跑，不受本轮影响**：业主已定的方向是「把 Rapfi 思考时间补到 10000 ms」，
   问的是「抬时间还涨不涨」，与版本排序无关。它已于 2026-10-05 02:30 起在 box 上串行开跑
   （`--ladder L4 --batch rapfihi1`，10 对 × 20 = 200 局；box 已同步到含 §1 警告的 main）。
   读完 L4 才能回答「要不要继续抬时间」，也才轮到「要不要花 15–23 小时排版本名次」这个决策。
3. **给业主的两个选项（推荐第一个）**：
   - **A（推荐）**：接受「这三个版本不可分」，把 box 时间全部投给 **Rapfi 曲线**（L4 已在跑；若曲线还在涨，
     再补 `@20000`/`@30000` 之类上限档）。理由：排序的代价（15–23 h）换来的可能是「分不出来」，
     而曲线的结论直接服务于顶层目标（「胜率稳步上升后抬 Rapfi 时间」）。
   - **B**：执意要名次 ⇒ 只挑**最有价值的一对**（本轮 `v11 vs v14` 是唯一一对 42.5% vs 57.5% 且带 11 和的对）
     堆 100 局配对（≈7.7 h），而不是跑整张 L1。
4. **版本线到此的总结**：v9 → v14 六个版本对 Rapfi 都已是「明显更强」，而**版本之间自 2026-10 起进入平台期**
   （L2 的 12 对区间重叠 + 本轮的闭环）。要继续从机制上要收益，需要的是**能分辨 5 pt 的配对样本**，
