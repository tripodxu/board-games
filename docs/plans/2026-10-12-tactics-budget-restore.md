# 2026-10-12 · 防守预算回退挑战轮（`v14.3` vs `v14-plus`）—— 预注册

> **本文在实验提交前写死**（提交时间见文末）。判据、数据、结论口径都以本文为准，
> 事后不得改判据再来解释结果。做法沿用 [ADR-0023](../adr/0023-v14-plus-integration.md) 增补一～五的预注册惯例，
> 规则依据见 [AGENTS.md](../../AGENTS.md) §2 硬性规则 10–11。

## 一、动机：来自 `vplus-r10s` 挑战轮的败局深挖

`vplus-r10s`（v14-plus vs Rapfi@10s，120 局，2026-10-12）打出 **69 胜 / 9 和 / 42 负**，
得分率 61.3%、不败率 65.0%。但执色拆分暴露了真问题：**执黑 39/60 = 65.0%、执白 30/60 = 50.0%**——
优势几乎全来自先手，执白只是打平。

42 局败局的形态高度一致：**全部被五连结束、最后一手走的都是 `block` 层**，
不可逆点那一手 **27/42 落在 `parry` 层**（`parry` 是接管链里最弱的兜底防守层，
真防线 `vcfDefense`/`vctDefense` 没开火才轮到它）。

### 逐手探针（`.work/analyze-loss.mjs`，42 局败局 × 尾部 12 个我方手位 = 501 个局面）

| 指标 | 值 | 读法 |
|---|---|---|
| **漏杀（开 sound 闸门，生产口径）** | **0 / 501** | 攻方一侧干净：我们有强制胜却走防守层的局面 **一处也没有** |
| 漏杀（关 sound 闸门） | 63 / 501 | 全部是伪胜，被 v9 起的 `defenderWinsFull` 闸门正确滤掉 ⇒ **闸门在承重** |
| 对手有强制链的局面 | 323 / 501 | 对手大多数时候确实握着链 |
| **预算敏感位置**（现行 `8/2` 找不到拆链点、`24/8` 找得到） | **9** | 见下表 |

**9 个预算敏感位置逐个复测（`.work/budget-check.mjs`，三档对照 8/2 / 12/3 / 24/8）**：

| 局 | ply | 层 | 实走 | 链型 | 8/2 | **12/3（v14 原值）** | 24/8 | 是不是真失误 |
|---|---|---|---|---|---|---|---|---|
| g114 | 44 | parry | D9 | vcf | 无 | **F11** | F11,F12 | **是** |
| g14 | 36 | parry | C11 | vcf | 无 | **C12** | C12,B13 | **是** |
| g50 | 46 | block | C15 | vcf | 无 | C15 | C15 | 否（实走恰是拆链点） |
| g13 | 83 | live3Attack | N8 | vcf | 无 | 无 | D14 | 需远超原值 |
| g13 | 85 | live3Attack | E5 | vcf | 无 | 无 | D14 | 需远超原值 |
| g26 | 36 | vcfDefense | G10 | vcf | 无 | 无 | I7 | 需远超原值 |
| g58 | 66 | parry | M9 | vcf | 无 | 无 | J12 | 需远超原值 |
| g68 | 84 | vcfDefense | J5 | vcf | 无 | 无 | M5 | 需远超原值 |
| g80 | 62 | parry | M7 | vcf | 无 | 无 | K9 | 需远超原值 |

**因果链是闭合的**：`vctDefMax` 收到 8 之后，`vctDefense` 在这些局面里试满 8 个候选仍找不到拆链点
→ 本层不开火 → **降级到 `parry` 兜底**（而 `parry` 防的是「对手下一步造双杀」，与那条链不是一回事）
→ 实走了一个拆不掉链的点 → 崩。预算回到 v14 原值 12/3 之后 `vctDefense` 能开火、层选对。

**恢复原值能救的是 2 处真失误**（g114 ply44、g14 ply36）；另 6 处要 `24/8`（远超 v14 原值 2 倍）
才看得见——**那是加码，规则 10 与 `tactics-budget.ts` 的「只减不增」纪律都禁止，本轮不做**。

### 两个否证（诚实记账）

1. **预算不是唯一原因**：`parry` 层的 31 个局面里有 27 个，**即使 24/8 也找不到任何拆链点**——
   那些链在 `parry` 开火时**已经拆不掉了**，失误发生在更早的「没让链成型」，不是拆链失败。
   本轮不碰那个问题（需要新机制，属规则 10 的另一类议题）。
2. **攻方没有可修的缺陷**：漏杀 0/501。sound 闸门在正确地滤伪胜，动它就是拆承重墙。

## 二、挑战者：`v14.3`（单变量）

`v14-plus` 与 `v14.3` 的 `mech` 集合**逐键相同**，差别只有三个预算键（程序化核对，非读 note）：

```
v14-plus vs v14.3 :  mech []  |  budget ["vctDefMax 8→12","vctDefKeep 2→3","pressureCutMax 80→120"]
v14-plus vs v14.1 :  mech ["softGate"]  |  budget [同三个]      ← 双变量，不可用于归因
v14.3    vs v14.1 :  mech ["softGate"]  |  budget []            ← 单变量（备用臂）
```

**为什么不新建 `v14.4`**：`v14-plus` 把那三个键撤回去，得到的 `mech` + 预算组合与已登记的 `v14.3`
**行为逐字相同**。再造一个 id 会得到一个行为完全重复的档位，登记表失去「一档一行为」的归因意义，
还要多付 14 局面指纹与档位自检的维护成本。`v14.1`/`v14.3` 当初就是为同一个理由撤掉了这批减法
（`v14.1` note：「比分可疑的减法全部退出」），而 `vplus2` 那 436 局**从未单独隔离过这三个键**。

**合规自查（规则 10「战术层不吃搜索」）**：本轮是**把已被本项目判定为「比分可疑」的减法撤回**，
不是加深搜索——`vctDefMax` 12 与 `vctDefKeep` 3 都是 **v14 上线时的历史常量**，本档的
`fidelity: 'exact'` 指的正是「与 v14 逐字一致」。攻击侧预算一个不动（`vctPlies 9` /
`vcfNodeLimit 4000` / `live3` 两层），与减法版的原设计一致。

## 三、预注册判定规则（跑前写死）

### 实验 A：`v14.3` vs `v14-plus`（jevrouter 双臂，同开局换色配对）

| 判据 | 层级 | 通过条件 |
|---|---|---|
| **机制层：拆链层开火率** | **主** | `v14.3` 臂的 `vctDefense` 开火手数 **高于** `v14-plus` 臂，且 `parry` 兜底手数 **低于** `v14-plus` 臂（这就是预算恢复的直接可观测后果） |
| 规则 11：负局不增加 | 硬底线 | `v14.3` 臂负局数 **≤** `v14-plus` 臂 |
| 规则 11：不败率不下降 | 硬底线 | `v14.3` 臂不败率 **≥** `v14-plus` 臂 |
| 比分统计量 | **只报不判** | 逐对分差均值 + 配对 95% CI，照 `vplus2` 的口径报 |

**比分为什么只报不判**：本轮测得的效应量是「42 局败局里 2 处漏拆链」≈ 每局 1.7 个百分点。
按配对差的标准差约 0.5 估算，要让 95% 区间下界离开 0 需要约 **2000 对**（4000 局）——
本轮 60 对的样本量**在统计上根本没有功效**，跑了也不可能得出显著的比分结论。
`vplus2` 的教训（79 对时 CI 下界仅 0.0012 属擦线，加到 218 对才稳住）说明这个项目已经吃过
「用不足样本宣称提升」的亏。本轮**以机制层为主判据**，比分如实报、不用来下结论。

### 实验 B：`v14.3` vs Rapfi@10s

对照基准用刚跑完的 `vplus-r10s` 同条件轮（120 局，同 seed、同上游、同 store）：

| 判据 | 通过条件 |
|---|---|
| 负局不增加（规则 11 底线） | `v14.3` 臂负局 ≤ 42 |
| 不败率不下降 | `v14.3` 臂不败率 ≥ 65.0% |
| 执白拆分 | 单列汇报（`vplus-r10s` 执白仅 50.0%，这是要盯的重点，不是本轮要修的目标） |

## 四、执行参数

```bash

node scripts/experiment-batch.mjs submit --batch vdef-3v-p \
  --a "jevrouter:v14.3:0" --b "jevrouter:v14-plus:0" \
  --games 120 --pause 2500 --seed 20261012 --store local --upstream direct \
  --allow-production --host 185.242.234.48 --user root

# 实验 B：对 rapfi@10s，与 vplus-r10s 同条件
node scripts/experiment-batch.mjs submit --batch vdef-3r10 \
  --a "jevrouter:v14.3:0" --b "rapfi::10000" \
  --games 120 --pause 2500 --seed 20261012 --store local --upstream direct \
  --allow-production --host 185.242.234.48 --user root
```

**已知风险**：`vplus-r10s` 那轮 120 个槽位里有 54 个被上游 400 打废（`opencode2api does not expose`，
间歇性，11:15 恢复），缺口靠人工监督补齐。两轮都按同样方式盯；**收口判据是 `games.jsonl` 行数**，
不是 `round-summary.json` 存不存在（后者存在 ≠ 跑完，见 `remote-experiments.md` §2.5）。
